# JobMatch — Frontend

Веб-интерфейс JobMatch — сервиса поиска работы с ограниченным количеством откликов.

## Текущий результат

Подготовлен каркас по [задаче №7](https://github.com/CODEXSQUAD/jobmatch-docs/blob/main/planning/week-1/07-frontend-skeleton.md): React + TypeScript + Vite, React Router, TanStack Query и Material UI. Версии зависимостей зафиксированы в `package.json` и `package-lock.json`.

В документации проекта стек ещё имеет статус рабочего предложения: утверждение командой и преподавателем не зафиксировано. Каркас реализует стек из описания задачи; это не меняет статус согласования.

| Адрес | Что доступно |
|---|---|
| `/` | Главная страница и переходы к разделам |
| `/vacancies` | Заготовка каталога с явным сообщением о разработке |
| `/system` | Настоящий GET `/health`: загрузка, результат, ошибка, повторная проверка |
| Другой адрес | Страница 404 со ссылкой на главную |

Каталог с данными — отдельная задача №10. Авторизация, резюме, кабинеты, отклики, лимиты, Docker/Nginx и CI пока не реализованы. Бизнес-правила и списание лимита проверяет backend.

## Требования

- Node.js **24.x** и npm **11.x или 12.x** (npm поставляется с Node.js).
- Git; интернет для первой установки зависимостей.
- Для проверки API — соседний [jobmatch-backend](https://github.com/CODEXSQUAD/jobmatch-backend) с реализованным `/health` и .NET SDK по его `global.json` и README.

Проверьте инструменты перед установкой:

```bash
node --version
npm --version
```

Если Node старый или npm не найден, установите Node.js 24 и откройте новый терминал. На Windows команды `where.exe node` и `where.exe npm` помогают обнаружить старую копию Node в PATH. При использовании nvm версия указана в `.nvmrc`.

Docker и PostgreSQL для проверки текущего каркаса не нужны.

## Установка и запуск

Предполагается соседнее расположение репозиториев:

```text
JobMatch/
  jobmatch-frontend/
  jobmatch-backend/
  jobmatch-docs/
```

В первом терминале, из `jobmatch-backend`, выполните команды [README backend](https://github.com/CODEXSQUAD/jobmatch-backend#сборка-и-запуск):

```bash
dotnet restore
dotnet build --no-restore
dotnet run --project src/JobMatch.Api --launch-profile http
```

Ожидаемый адрес backend — `http://localhost:5140`. По `http://localhost:5140/health` ожидается HTTP 200 с `{"status":"ok"}`.

Во втором терминале, из `jobmatch-frontend`:

```bash
npm ci
npm run dev
```

Откройте [приложение](http://localhost:5173) и раздел [«Проверка API»](http://localhost:5173/system). Серверы работают до `Ctrl+C` в соответствующих терминалах. Frontend запускается и без backend; тогда проверка API показывает ошибку.

## Как запрос попадает в backend

Браузер обращается к тому же origin, откуда загружено приложение. Vite перенаправляет `/health` и `/api/...` в backend, сохраняя полный путь:

```text
браузер → http://localhost:5173/health → Vite proxy → http://localhost:5140/health
```

`/health` не находится под `/api`. Префикс `/api` у будущих endpoints тоже не удаляется. CORS для этого режима разработки не требуется.

Настройка по умолчанию работает без `.env`. Если backend запущен на другом порту, скопируйте `.env.example` в `.env` и задайте адрес, например:

```dotenv
API_PROXY_TARGET=http://localhost:5141
```

Перезапустите Vite после изменения. Это настройка сервера Vite; она не встраивается в браузерный код. Не добавляйте секреты в `VITE_*`: такие значения доступны пользователю браузера. `.env` исключён из Git.

## Сборка и проверки

Из `jobmatch-frontend`:

```bash
npm test
npm run build
npm run preview
```

- `npm test` проверяет API-клиент: контракт `/health`, HTTP/сетевые ошибки, тайм-аут, отмену запроса, некорректные ответы и HTTP 204.
- `npm run build` выполняет строгую проверку TypeScript и создаёт производственную сборку в `dist/`.
- `npm run preview` открывает сборку на [localhost:4173](http://localhost:4173). Для локальной проверки здесь также настроен proxy к backend.

`vite preview` предназначен для локальной проверки сборки. При размещении `dist/` на сервере нужно отдельно настроить раздачу `index.html` для маршрутов SPA и proxy `/health` и `/api/...` к backend. Docker/Nginx готовятся в задаче №11; Vite-конфигурация не переносится в статический хостинг автоматически.

Проверка 22.09.2026: `npm ci`, `npm run build` и 11 тестов прошли на Node.js 24.19.0 / npm 12.0.2. В браузере проверены переходы, история, прямое обновление маршрута, 404, узкий экран и цепочка с настоящим ASP.NET Core backend: успех → остановка backend → ошибка → перезапуск → успех. Производственная сборка через preview также получает ответ `/health`. Это локальная проверка; независимая приёмка Владом ещё ожидается.

## Приёмка Владом

1. Получить ветку с изменениями и выполнить установку и запуск по инструкции выше.
2. Перейти между главной, вакансиями и проверкой API; проверить кнопки назад/вперёд браузера.
3. Открыть `/system` напрямую и обновить страницу: маршрут должен работать.
4. При запущенном backend увидеть «Сервер доступен», HTTP 200 и `{"status":"ok"}`.
5. Остановить backend, нажать «Повторить проверку»: появится понятная ошибка, прежний успешный результат не должен оставаться на экране.
6. Запустить backend снова и повторить проверку: успех восстанавливается без перезагрузки приложения.
7. Открыть несуществующий адрес; проверить 404 и возврат на главную. Проверить навигацию на узком экране.
8. Выполнить `npm test` и `npm run build`, затем проверить `/system` через `npm run preview`.

Запуск на компьютере Влада и его ревью должны быть подтверждены отдельно. Сам факт создания каркаса не закрывает этот критерий.

## Если запуск не удался

| Симптом | Что проверить |
|---|---|
| `npm` не найден / ошибка версии Node | Версии инструментов и порядок записей PATH; нужен Node 24 |
| Порт 5173 или 4173 занят | Остановить свой прежний сервер или запустить `npm run dev -- --port 5174` / `npm run preview -- --port 4174`; открыть указанный порт |
| HTTP 500/502/503 или нет соединения | Backend работает; `/health` отвечает напрямую; `API_PROXY_TARGET` соответствует адресу backend |
| Тайм-аут | Сервер не завершил запрос за 10 секунд; проверить backend и повторить запрос |
| Некорректный JSON / ответ `/health` | Проверить адрес proxy и контракт; HTML страницы не считается успешным health-ответом |
| .NET не находит подходящий SDK | Сверить `dotnet --list-sdks` с `jobmatch-backend/global.json`; одного Runtime недостаточно |

## Структура и дальнейшая разработка

```text
src/
  app/          маршруты, layout, тема
  pages/        главная, каталог-заготовка, проверка API, 404
  shared/api/   общий HTTP-клиент и запрос /health
tests/          проверки поведения API-клиента
```

`requestJson<T>(path, options)` принимает полный путь из контракта, поддерживает `RequestInit`, отмену через `AbortSignal` и `timeoutMs` (по умолчанию 10 секунд). Для JSON-запросов передавайте `body: JSON.stringify(data)`; заголовок `Content-Type` добавляется для строкового тела. Ошибки содержат сообщение, HTTP-статус и код, когда они доступны. Тип `T` не валидирует ответ во время выполнения; `getHealth` отдельно проверяет `status: 'ok'`. Для новых endpoints добавляйте проверку данных по согласованному контракту. Cookie передаются только в пределах origin; авторизация и CSRF-защита будут подключены вместе с соответствующими сценариями.

Health-запрос выполняется при входе на страницу и по кнопке; автоматические повторные попытки отключены, чтобы ошибка была видна. Во время повторной проверки прежние данные скрыты. `/health` подтверждает ответ API, но не соединение с PostgreSQL.
